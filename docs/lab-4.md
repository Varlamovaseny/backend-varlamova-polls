# Лаба 4. Веб-страница и безопасность в браузере

Страница в браузере, которая работает с API: список записей, вход, создание и удаление, понятные ошибки. Текст из базы выводится как текст, без `innerHTML`. Если страница и бэкенд на разных портах, на бэкенде настроен CORS. Подойдёт чистый HTML и JavaScript или любой фреймворк. Скриншот интерфейса в README.

Срок: PR из `lab-4` в `main` до 23:59 накануне встречи 5.

## Чек-лист базы (6 баллов)

1. Страница открывается и загружает список с API, это видно во вкладке Network
2. Форма входа: без входа изменять нельзя (кнопок нет или понятная ошибка)
3. Создание и удаление через интерфейс
4. Ошибки 400, 401, 404 показываются понятным текстом
5. XSS: опасная строка показывается текстом
6. CORS настроен, или страницу отдаёт сам бэкенд

## ★ (2 балла): редактирование, связанная сущность, заголовки

Все три части дают 2 балла, две дают 1.

- Редактирование записи через интерфейс.
- Страница записи со списком связанных записей и формой добавления.
- Ответы API с `X-Content-Type-Options: nosniff`, у страницы `Content-Security-Policy` без `'unsafe-inline'` в `script-src`.

## ★★ (2 балла): cookie и CSRF или обновления в реальном времени

Один из двух вариантов.

- **(а)** Вход через cookie с флагами `HttpOnly` и `SameSite`, токена в `localStorage` нет. Запрос с cookie с чужого сайта без CSRF-токена получает 403.
- **(б)** Запись, созданная в одном окне, сама появляется во втором без F5: Server-Sent Events или WebSocket.

## contract.json: что добавить

```json
{
  "frontend_url": "http://localhost:5173",
  "cookie": { "login_path": "/auth/session" },
  "realtime": { "type": "sse", "path": "/api/events" }
}
```

`cookie` нужен только для варианта (а), `realtime` только для (б). Для WebSocket `"type": "websocket"`.
