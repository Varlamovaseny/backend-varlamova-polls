# Лаба 5. Docker и соседние сервисы

Проект поднимается одной командой `docker compose up`: бэкенд, база, страница и второй сервис. У бэкенда свой `Dockerfile`, данные базы в именованном volume, настройки из `.env`, в репозитории `.env.example`. Второй сервис работает в отдельном контейнере, основной обращается к нему по HTTP по имени сервиса. Если второй сервис недоступен, основной отвечает 503. Каждый запрос пишет строку лога в stdout.

В репозитории нужен файл `.github/workflows/backcheck.yml`:

```yaml
name: backcheck
on:
  pull_request:
  workflow_dispatch:
jobs:
  backcheck:
    uses: bozhedom/backcheck/.github/workflows/lab5.yml@v1
```

Срок: PR из `lab-5` в `main` до 23:59 накануне встречи 6.

## Чек-лист базы (6 баллов)

1. Dockerfile для бэкенда
2. `docker compose up` поднимает всё, проверка на чистой машине зелёная
3. Данные в volume: после `down` и `up` записи на месте
4. Настройки через `.env`, `.env.example` есть, секретов в git нет
5. Второй сервис: основной ходит в него по HTTP, при его остановке отвечает 503
6. Каждый запрос пишет строку лога, её видно в `docker compose logs`

## ★ (2 балла): CI и прокси

Каждая часть даёт 1 балл.

- Свой workflow в GitHub Actions: сборка и минимум 3 автотеста API (создание, 404, 401).
- Nginx (или Caddy, Traefik) как единая точка входа: на `/` страница, на `/api` бэкенд.

## ★★ (2 балла): кэш, брокер, деплой, любые два из трёх

Две части из трёх дают 2 балла, одна даёт 1.

- Кэш в Redis для тяжёлого запроса с заголовком `X-Cache: HIT` или `MISS`, после изменения данных кэш сбрасывается.
- Событие через брокер сообщений (RabbitMQ, Redis, Kafka, NATS), его читает отдельный сервис-получатель.
- Публичный деплой по `https://`.

## contract.json: что добавить

```json
{
  "compose_service": "backend",
  "second_service": {
    "name": "reports",
    "trigger": { "method": "POST", "path": "/api/books/{id}/loans", "body": { "reader": "Иванов", "taken_at": "2026-10-01" } },
    "expect_when_down": [502, 503, 504]
  },
  "proxy_url": "http://localhost:8080",
  "cache": { "path": "/api/books/stats", "header": "X-Cache" },
  "broker": {
    "consumer": "notifier",
    "trigger": { "method": "POST", "path": "/api/books/{id}/loans", "body": { "reader": "bc-{tag}", "taken_at": "2026-10-01" } }
  },
  "public_url": null
}
```

| Поле | Что писать |
| --- | --- |
| `compose_service` | Имя сервиса бэкенда в compose |
| `second_service.name` | Имя второго сервиса в compose |
| `second_service.trigger` | Запрос к основному сервису, во время которого он обращается ко второму. `{id}` заменяется на id новой записи, которую создаст чекер |
| `proxy_url` | Только для ★: адрес прокси |
| `cache` | Только для ★★: адрес, ответ которого кэшируется, и имя заголовка |
| `broker.consumer` | Только для ★★: имя сервиса-получателя в compose |
| `broker.trigger` | Только для ★★: запрос, после которого уходит событие. Вместо `{tag}` чекер подставит метку, она должна попасть в строку лога получателя |
| `public_url` | Только для ★★: публичный адрес с `https://` |
